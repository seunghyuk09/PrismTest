# 시작 전 확인이 필요한 사항

에이전트를 실제로 돌리기 전에 아래가 정해져야 설계가 헛돌지 않습니다.
(모르면 "모름"으로 두고 진행 — 가정으로 채우면 나중에 전부 다시 합니다.)

## 1. 대상물
- [ ] 프리즘 실제 치수 (빗변/직각변 길이, 높이) — 시야·배율·최소 초점거리 계산의 기준
- [ ] 재질: 유리(BK7 등) / 아크릴 / 기타
- [ ] 검사 대상면: 몇 개 면을 봐야 하는가? (빗변 1면만? 3면 전부?)
- [ ] 검사 시점의 도장 유무 — 사진은 흑색 도장품, 실검사는 투명이라 하셨는데
      같은 품목의 다른 공정 단계인지 확인 필요
- [ ] 반사코팅(AR 등) 유무

## 2. 결함 기준
- [ ] 검출해야 할 **최소 얼룩 크기** (mm). 이 값이 카메라 해상도·촬영거리를 결정
- [ ] 고객 스펙 문서 유무 (scratch-dig 등급, 허용 결함 수/크기)
- [ ] 표면 얼룩 5,843건 중 **재세정으로 사라지는 비율** — 진짜 얼룩인지 분류 오염인지
- [ ] 한도견본(양품/한도/불량) 현물 보유 여부

## 3. 운영 조건
- [ ] 일 검사 물량, 목표 택트타임(개당 몇 초)
- [ ] 현재 검사 인원 및 검사원 판정 편차 파악 여부
- [ ] 미검 1건의 실제 비용(후공정 손실/고객 클레임) vs 과검 1건 비용
- [ ] 검사 장소 조명 환경(형광등/LED, 창가 여부)

## 4. 장비
- [ ] 갤럭시 Z 폴드 7 실기 확보 여부, 개발자 모드/사이드로드 가능 여부
- [ ] Android Studio 빌드 환경 (이 세션 컨테이너에는 Android SDK가 없을 수 있음)
- [ ] 지그 제작 수단: 3D 프린터 / 알루미늄 프로파일 / 외주
- [ ] 조명 부품 조달 가능 여부 (LED 바, 확산판, 편광필름, 흑색 플로킹지)

## 5. 크로스플랫폼 (iOS 지원) — 상세는 `docs/platform-strategy.md`
- [ ] **실제로 현장에서 쓸 기종**이 무엇인가? (검사자 개인 폰? 회사 지급 폰 통일?)
      → 기종이 통일되면 캘리브레이션 공수가 크게 줄어든다. 가능하면 통일을 권장
- [ ] 우선 지원할 2~3기종 선정 (전 기종 지원은 기종당 검증 공수가 든다)
- [ ] **Apple Developer Program 가입 가능 여부** ($99/년) — iOS는 사이드로드 불가
- [ ] **macOS + Xcode 사용 가능한 맥이 있는가?** 없으면 iOS 빌드 자체가 막힘
- [ ] 회사 MDM(모바일 기기 관리) 운영 여부 — 있으면 배포가 훨씬 수월
- [ ] 검사에 쓸 폰 대수 (Ad Hoc 100대 제한 / TestFlight 선택 기준)

## 권장 진행 순서
1. `prism-defect-taxonomy` → 얼룩 라벨 순도 확인 + 한도견본 정의  ← **여기가 먼저**
2. `prism-optics-jig` → 조명 후보 3안 비교 촬영, ΔI/I 실측으로 1안 선정
3. `prism-vision-algo` → Python 프로토타입, ROC로 검증
4. `prism-calibration` → 임계값 확정, GRR
5. `prism-mobile-app` → C++ 코어 + Android 셸, 수치 일치 검증, 파일럿
6. iOS 셸 추가 → 기기 등가성 검증 → 기종 확대

**1~5는 Z 폴드 7 한 대로 끝낸다.** 알고리즘이 확정되기 전에 기기를 늘리면
문제가 알고리즘 탓인지 기기 탓인지 구분할 수 없다. 단, 코드 구조는 처음부터 공용 C++ 코어.

2번에서 조명으로 얼룩이 확실히 보이지 않으면 3~5번은 진행해도 실패합니다.
**첫 실물 실험(조명 3안 비교 촬영)이 이 프로젝트의 최대 분기점입니다.**
